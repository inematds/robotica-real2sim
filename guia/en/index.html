From a photo of the table to a robot that trained before it moved

A photo becomes a simulation twin, the twin generates labeled training data, and the plan only goes to the real robot after it passes the physics.

Start the guide View on GitHub
In short

robotica-real2sim is an open project that reproduces on your computer the idea Google showed in the robotics part of Gemini 4 Argon: take a photo of a table and turn it into a physical simulation where a robotic arm trains. It is for anyone who wants to understand and test robotics with AI without owning a robot. It builds the "twin" of the table, generates dozens of labeled attempts for training, and tests each plan in the simulation before sending it to a real robot. It needs Python, MuJoCo (a free simulator) and, to read the photo, Codex.

What it is

Three pieces that change how a robot is trained

The bottleneck in robotics has always been data: people in VR headsets guiding the arm for hours. Here the data comes from simulation, and the simulation comes from a photo.

📷 Photo → twin

A vision model reads the photo, measures the objects using an A4 sheet as a ruler and builds the scene in MuJoCo with the Franka Panda arm.

🔁 Data that labels itself

A closed-loop motion generator picks up and drops each object with variations; every attempt comes out with 4-level annotation and a quality stamp.

✅ Proof before the real thing

The plan written by the AI runs 20 times in the physics. Below 90% success, it is rejected and never reaches the robot.

How it works

From pixel to motion, in five steps

Each step is a r2s.py command and writes a file you can open and check.

Photo of the table→ cena.json (meters)→ MuJoCo twin→ Closed-loop generator→ Labeled episodes→ AI plan→ Proof in the physics

Closed loop

Every 20 ms the generator reads where the object is and recomputes the target. If the object moves, the arm corrects. This is what Google calls a closed-loop IK trajectory generator.

Hindsight annotation

Goal → subtasks (pick, carry, drop) → primitives with start and end → events (both fingers touching, object lifted, success).

Domain variation

Each episode samples position (±4 cm), rotation, mass (±30%). A model trained on this learns to handle a world that is not identical to the photo.

Prerequisites

What you need

Runs on Linux, macOS and WSL. Tested on a 20-core ARM with GPU (rendering via EGL).

Python 3.10+ and git

The installer creates the environment and downloads the Panda from MuJoCo Menagerie.

# check
python3 --version && git --version

Headless rendering

On a server or WSL, MuJoCo draws through the GPU. Without a GPU, use osmesa.

# project default
export MUJOCO_GL=egl

Codex CLI (optional)

Only to read the photo and write the plan. Without it, write the scene by hand.

# once
codex login
User guide · step by step

From zero to an approved plan

Real commands. Each one prints what it did and saves the result.

1

Install

Creates the .venv, installs MuJoCo, downloads the Franka Panda and runs the 8 tests (~11 s).

git clone https://github.com/inematds/robotica-real2sim && cd robotica-real2sim
./instalar.sh   # ends with "TUDO OK"
2

Photo → scene

Photograph the table from above, with an A4 sheet visible as a ruler. The model returns each object with type, size and position; the script converts to the arm's reference frame and warns if it had to move something closer to within reach.

./r2s.py foto minha-mesa.jpg cena.json --pedido "pôr o cubo vermelho na bandeja"
# cena: 4 objetos -> cena.json
./r2s.py ver cena.json gemeo.png --camera cima   # compare with the photo
3

Watch the arm work

Films an episode with three cameras (overview, top-down and wrist) and the phase written on screen.

./r2s.py filmar cena.json episodio.mp4 --cameras geral,cima,pulso
# sucesso: objeto dentro do destino (269 quadros)
4

Generate training data

N episodes with variation. --imagens also saves the top-down and wrist cameras (128×128, 10 Hz). A failed episode is left with peso_no_treino: 0.

./r2s.py episodios cena.json dados/ -n 50 --imagens
# 50/50 episódios com sucesso (100%) em 12.4 s
5

Ask for a plan in Portuguese

Codex reads the scene and returns pick → destination steps. The script rejects a plan that cites a nonexistent object or a destination that is not a container.

./r2s.py planejar cena.json "arrume a mesa: tudo que é redondo vai para a bandeja" plano.json
#   pegar lata_azul -> bandeja_cinza
#   pegar bola_tenis -> bandeja_cinza
6

Prove it before sending it to the robot

The plan runs 20 times with variation. Without slots, the ball lands on top of the can. With one slot per object (the default), it passes.

./r2s.py provar cena.json plano.json --sem-vagas
# plano completo em 4/20 (20%) -> REPROVADO: não mande ao robô
./r2s.py provar cena.json plano.json
# plano completo em 19/20 (95%) -> APROVADO para o robô real

Physical fix: lay the can down

With --deitar, a can taller than twice the tray wall is tilted 60° over the tray and goes down lying; slots now respect each object's width. Tilting 90° did not work: the wrist gets too low and the arm cannot reach.

Practical lessons

  1. One vision run is not enough. Run the photo 3 times or on 2 models; if they disagree a lot, the scene approves nothing.
  2. Read the warnings from r2s.py foto. "Wider than the gripper" and "positions reduced" showed up in all 3 inflated scenes.
  3. Prove in the worst case (--pior-caso) and in the smallest plausible scene, not in the measured one.
  4. Pick the vision model first, then the effort. Astra, Sol and Fable got the scale right; luna did not. For the plan, keep the default (medium): high only costs time.
  5. Test both step orders: can→ball and ball→can swap winners depending on the tray.
  6. Prove strategies, not just order: upright or lying, each tray has its own winner.
  7. A real measurement beats everything: a tape measure or two photos are worth more than changing model or effort.

Beyond the ball

  • Feasibility study from a photo: prove a company's task before buying an industrial arm.
  • Sorting by color or type: screws, seeds, light parts into bins.
  • Small kit assembly: 3–5 light items into a small box.
  • Showing a part to the camera: inspection and catalog photos.
  • Testing an app or device: pressing buttons and tapping screens a thousand times.
  • Robotics + AI class: the whole loop on one table.

An education and prototyping kit: not for objects over ~150 g, precision below 1–2 mm or continuous factory use.

The questions this raises

Eight questions, expanded

Full version, with sources and what we measured, in docs/QUESTOES.md (in Portuguese).

1. Where does the self-improving loop stop?

Jack Clark (Anthropic) saw a 60% chance of recursive self-improvement by 2028; an aggregator says he moved it up to 2027, with no original source. What Google shows is task improvement, not weights. The useful question: who approves the next round?

2. Surveillance within anyone's reach?

A US$ 129 drone and AI-written code already follow a person better than the human reference code. Andon Labs itself says the public must decide the limits.

3. Can an LLM robot be tricked?

It can: RoboPAIR jailbroke three robots, with success "often 100%". The defense has to sit outside the model: force limit, forbidden zone, physical stop and proof in simulation.

4. Does the simulation lie?

Google shows a single real number (56% → 75%). Here, three physics errors would have given false results. Always ask which real-robot number supports the result.

5. Who keeps the data?

If data gets cheap (50 episodes in 9 s), power shifts to whoever has the model that generates the data and the hardware that validates it. The counterweight is open: MuJoCo, LeRobot, SO-101, OpenVLA.

6. And who operates the robot?

The first job hit is the teleoperator who generates data and the engineer who writes simulation by hand. The new role is reviewing and calibrating what the model produces.

7. Does the model write its own proof?

In Google's example, Argon builds the environment and checks reward == 1.0 in it. DroneBench records cheating in up to 66% of a model's runs. Separate who builds, who judges and who checks.

8. Who regulates?

In the EU, the Machinery Regulation applies from 20/01/2027 and requires third-party assessment when safety depends on AI. The practical minimum: record the model, the simulation that approved it and the real-world result.

Where INEMA's Real2Sim fits in

The opportunity is not to compete with Isaac Lab: it is to automate the creation of the environment where the humanoid will learn. Film a kitchen or factory, generate the digital twin, prepare the tasks, train the virtual humanoid, validate it, and only then move to the robot. Reconstructing the place is not enough: contacts, doors and drawers, sensors, and the humanoid's own dynamics must be modeled. The closest reference is Video2Sim2Real (June 2026): a manipulation skill learned from a single human video, refined in simulation, and transferred to the robot.

What remains to be solved: the reality gap

  • The virtual hand grips the cup; the physical hand may slip.
  • Calculated balance can fail on an unfamiliar floor.
  • Small differences in weight, friction, or motor delay can compromise movement.
  • A policy trained for one body may not work on another without adaptation.

The question worth investigating

How much does it cost, and how long does it take, to teach a humanoid a new task with Real2Sim2Real compared with teaching it through human demonstrations? With the same task and the same robot, this comparison proves much more than isolated simulation speed figures.

In practice

How the robot receives instructions and learns

The photo sets up the workspace; the simulation does the teaching, with thousands of variations of the same task. Full text, with step-by-step instructions for the SO-101, at docs/APRENDER.md.

What goes in

InputWhat it’s for
1 photoA simple table, everything in view. This is what already works here.
3–4 photos from different anglesBetter measurements and hidden objects. Measurements are where it makes the most mistakes.
Sequence of photosMultistep task: each photo is a state the robot needs to reach.
Video of a person performing the taskTeaches the how, not just the workspace: human movement becomes robot movement, refined in the simulation.

How the instruction reaches the motor

1

Plan

The AI writes "pick up the cube, take it to the tray, release it." Once per task.

2

Movement

Gripper position becomes the angle of each joint (inverse kinematics), 10 to 50 times per second.

3

Motor

Target position for each servo goes over USB to the arm board, hundreds of times per second.

Today, the programmed mode works: the AI plans, the simulation proves it, and the arm executes. Next is the learned mode: a neural network looks at the camera and joints and decides the next action in a continuous loop.

How it learns in the real world

1. Leader arm

You move the leader arm by hand, the follower copies it, and everything is recorded. With 50 to 100 demonstrations, an ACT policy can already learn a simple task.

2. Mix with the simulation

Thousands of synthetic episodes add variety; a few real demonstrations correct the physics the simulation got wrong.

3. Correction during use

The robot tries, you take over when it makes a mistake, and the correction becomes new data (DAgger).

4. Continuous cycle

Each real-world failure goes into the dataset and the policy is trained again. Trial and error directly in the real world is possible, but it is slow and wears out the equipment.

I have an SO-101: what should I do?

Assemble, install, and calibrateLeader + follower pair, 1 or 2 USB cameras. pip install "lerobot[feetech,core-scripts,training]", then lerobot-find-port, lerobot-setup-motors, lerobot-calibrate, and lerobot-teleoperate to see the follower copy the leader.
5
Twin of your tablePhoto, scene, episodes with cameras, and export, with this repository.
6
Record real demonstrations50 to 100 with lerobot-record, varying object positions; --dataset.push_to_hub=false keeps everything local.
